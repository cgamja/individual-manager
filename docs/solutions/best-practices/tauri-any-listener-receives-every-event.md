# 창별 이벤트는 `emit_to`만으로 안 된다 — 전역 `listen()`이 `Any`라 전부 받는다

## Context

펭귄을 한 마리에서 여러 마리로 늘리자(창 하나 = 펭귄 하나), **모든 펭귄이 같은 시각에
같은 대사를 말하고, 한 마리를 때리면 전부 방망이를 휘두르는** 증상이 나왔다.
이동만은 제각각이었다.

"이동만 다르다"가 결정적인 단서였다 — 창 위치는 Rust가 `set_position`으로 창마다 직접
옮기고, 나머지(대사·빠따·동작 CSS)는 전부 **이벤트**로 간다. 즉 이벤트만 새고 있었다.

## Guidance

1. **`Emitter::emit`은 창에서 불러도 "모든 대상"에 보낸다.** `window.emit(...)`이
   그 창에 보내는 것처럼 읽히지만 아니다. 문서에도 *"Emits an event to all targets"*로
   적혀 있다. 한 창에 보내려면 `emit_to`다.

2. **그런데 `emit_to`만 고쳐도 아무것도 달라지지 않는다.** 프론트의 전역
   `listen()`(`@tauri-apps/api/event`)은 리스너를 **`{kind: 'Any'}`** 로 등록하고,
   Tauri는 `Any` 리스너를 **emit 대상과 무관하게 전부** 호출한다:

   ```rust
   // tauri-2.11.5/src/event/listener.rs:310
   *target == EventTarget::Any || filter.as_ref().map(|f| f(target)).unwrap_or(true)
   ```

   `Any`가 먼저 단락 평가되어 필터를 아예 보지 않는다. **보내는 쪽과 받는 쪽을 같이
   고쳐야 한다.**

3. **받는 쪽은 창에 묶인 리스너를 쓴다.**

   ```ts
   // 안 된다 — 대상이 Any라 남의 창 이벤트까지 전부 받는다
   listen<T>(EVENT, handler);

   // 된다 — {kind: 'WebviewWindow', label}로 등록된다
   getCurrentWebviewWindow().listen<T>(EVENT, handler);
   ```

4. **창이 하나일 때는 이 버그가 존재하지 않는다.** 그래서 멀쩡히 돌던 기능을 여러 창으로
   늘리는 순간 처음 드러난다. 창을 늘릴 때는 이벤트 경로를 **먼저** 점검한다.

## 안 통한 시도

- **`window.emit` → `window.emit_to(EventTarget::webview_window(window.label()), ...)`**
  — 보내는 쪽만 고친 것. 빌드도 통과하고 논리적으로도 맞아 보였지만 **증상이 하나도
  변하지 않았다.** 받는 쪽이 `Any`인 한 필터는 평가조차 되지 않기 때문이다.
  "고쳤는데 그대로"라면 반대쪽 끝을 의심한다.

- **펭귄마다 시드를 다르게 준 것** — 필요한 변경이긴 했다(같은 시드면 정말로 똑같이
  움직인다). 하지만 이 증상의 원인은 아니었다. 실제로 시드는 이미 달랐고, 그래서
  Rust가 계산한 **이동만** 제각각이었던 것이다. 증상의 일부만 설명하는 가설을
  원인으로 채택하면 안 된다.

- **첫 대사 시각을 각자 뽑게 한 것** — 이것도 진짜 버그였다(시작 시 한꺼번에 만들어진
  펭귄들이 고정 7초 뒤 다 같이 첫마디를 했다). 다만 첫 한 번만 설명하고 "계속 똑같이
  말한다"는 설명하지 못했다. **증상이 계속되는데 일회성 원인을 고쳤다면 아직 못 찾은 것이다.**

## 함께 밟은 함정 — 자가 치유가 정상 동작을 취소한다

같은 작업에서, 삭제 실패로 남는 "유령 창"을 정리하려고 틱에 **상태와 창을 대조해 정리하는
로직**을 넣었더니 **펭귄 추가가 아무 일도 하지 않게** 됐다. 추가는
(1) 상태에 넣고 (2) 창을 만드는 두 단계인데, 그 사이 20Hz 틱이 끼어들어 "상태엔 있는데
창이 없다"고 판단해 지워 버린 것이다. 에러도 남지 않는다.

**여러 단계로 이뤄진 변경을 감시하는 정리 로직에는 유예가 필요하다.** 여기서는 어긋남을
처음 본 시각을 기록하고 1초가 지난 것만 정리한다(`due_for_cleanup`). 그리고 그 판단은
**순수 함수로 떼어 테스트한다** — 틱 스레드 안에 두면 "정상 동작이 조용히 취소되는"
증상이 눈으로만 잡힌다.

## 예방

- 같은 문서를 여러 창에 띄우는 기능을 만들면, **첫 커밋 전에** "창 A의 조작이 창 B에
  보이는가"를 손으로 확인한다. 단위 테스트로는 잡히지 않는다.
- 증상이 여러 개일 때 **전부를 설명하는** 원인을 찾는다. 일부만 설명하는 수정은
  진짜 원인을 가린다.
- 보내는 쪽을 고쳤는데 그대로면 받는 쪽을, 받는 쪽을 고쳤는데 그대로면 보내는 쪽을 본다.
