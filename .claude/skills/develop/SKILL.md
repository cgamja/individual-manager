# develop — 마일스톤 항목 하나를 PR까지

이 레포의 작업 단위는 항상 **`TODO.md` 체크박스 하나**다. 그 단위를 지키는 게 이 스킬의 핵심이고,
나머지는 그 단위를 안전하게 끝내기 위한 게이트들이다.

전제 지식은 `CLAUDE.md`에 있다 — 문서 권위 순서, 명령어, 커밋·브랜치·테스트 컨벤션, 코드베이스 함정.
여기서는 그걸 반복하지 않고 **언제 무엇을 확인하고 언제 멈추는지**만 다룬다.

---

## 1. 범위를 하나로 좁히고, 막힌 게 없는지 본다

먼저 `TODO.md`를 읽고 작업할 체크박스를 **정확히 하나** 특정한다. 사용자가 "M2 하자"처럼 마일스톤
단위로 말하면 그 안의 첫 미완료 항목으로 좁히고, 무엇을 골랐는지 한 줄로 알린다.

그다음 **"시작 전 결정" 섹션의 미완료 항목**을 확인한다. 이건 형식적인 절차가 아니라 실제로 자주
막히는 지점이다 — 예를 들어 Notion TODO 조회를 구현하려면 기존 DB에 상태 속성이 있는지 알아야
스키마를 설계할 수 있고, 그건 사용자가 자기 Notion을 열어봐야 아는 정보다.

고른 항목이 미완료 결정에 의존하면 **구현을 시작하지 말고 사용자에게 물어본다.** 무엇이 필요하고
왜 필요한지, 어떤 선택지가 있는지를 같이 제시해서 한 번에 답할 수 있게 한다. 답을 받으면
`TODO.md`의 해당 결정을 체크하고 결론을 `PRD.md`에 반영한다. 서비스별 결정이면 `SERVICES.md`에도
반영한 뒤 진행한다 — 예를 들어 Notion DB 스키마 확인 결과는 `SERVICES.md`의 Notion 항목에 남아
있는 "확인 필요" 줄을 대체해야 한다. 그러지 않으면 다음 플랜이 이미 해소된 사항을 미해결로 읽는다.

의존하지 않는다면 바로 2단계로 간다.

**이 시점에서 멈춰야 하는 다른 경우:**
- 요청이 `TODO.md`에 없는 새 기능이다 → 기획 변경이므로 PRD 개정 여부를 먼저 사용자와 정한다.
  임의로 PRD를 고치거나 TODO에 항목을 추가해서 진행하지 않는다. **"일단 실험 브랜치로 만들어
  보고 나중에 문서를 맞추자"는 선택지를 제안하지 않는다** — 그렇게 만든 코드는 검토 없이
  남아서 PRD와 코드가 갈라지는 원인이 된다. 넣을지 말지를 먼저 정하는 게 항상 더 싸다.
- 요청이 체크박스 여러 개에 걸친다 → 어떻게 쪼갤지 제안하고 첫 항목만 진행한다.

### 멈출 때는 사용자가 한 번에 답할 수 있게 묻는다

게이트에 걸려 멈추는 건 흔한 일이고, 여기서 대화가 몇 번 왕복하면 그 자체가 비용이다.
멈출 때는 **무엇이 왜 필요한지 + 선택지 + 내 추천 + 추천대로면 어떻게 답하면 되는지**를 함께
제시한다. 사용자가 자기 계정을 열어봐야 아는 정보(DB ID, 스키마, 스코프 승인 여부)라면
어디서 어떻게 확인하는지도 적는다.

토큰·자격증명은 채팅에 붙여넣지 말라고 명시한다. 필요한 건 대개 식별자(DB ID, 워크스페이스
이름)이지 시크릿 자체가 아니고, 대화에 남은 시크릿은 회수할 수 없다.

## 2. 리서치하고 플랜을 쓴다

**엔진은 `ce-plan`이다 (필수).** 플랜을 직접 손으로 쓰지 않는다 — `ce-plan`을 호출하고 그 산출물을
아래 형식·체크리스트에 맞춘다. 쓰지 않기로 판단했다면 그 이유를 사용자에게 먼저 보고하고 동의를
받는다. 자세한 건 "compound-engineering 엔진" 절.

구현 전에 `docs/plans/YYYY-MM-DD-NNN-<타입>-<슬러그>-plan.md`로 플랜 문서를 만든다.
번호(`NNN`)는 기존 파일 중 가장 큰 값 +1이다. 형식과 각 섹션이 무슨 역할인지는
`references/plan-template.md`를 읽는다.

플랜을 따로 쓰는 이유는 M1에서 증명됐다 — 이 앱의 어려움은 로직이 아니라 **OS 통합 표면**에 있고,
그건 코드를 쓰기 전에 조사해야 알 수 있다. 숨겨진 웹뷰의 타이머가 5분 뒤 멈춘다는 걸 모르고
`setInterval`로 짰으면 전부 다시 짰어야 했다. M2~M6는 외부 API가 붙으므로 rate limit, 인증 만료,
페이지네이션, 응답 스키마가 같은 성격의 조사 대상이다.

리서치는 웹 검색과 코드베이스 조사를 병행한다. 관련 `docs/solutions/` 문서는 반드시 먼저 읽는다.

플랜을 다 쓰면 **구현 전에 사용자에게 보여주고 확인을 받는다.** 특히 Key Technical Decisions와
Assumptions는 여기서 틀리면 뒤가 전부 흔들린다.

### 플랜이 통과해야 하는 원칙 체크리스트

일반적인 코딩 관례로는 안 잡히고 이 프로젝트에서만 요구하는 것들이다. 해당되는 항목마다
플랜에 답이 있어야 한다.

- **외부 서비스에 쓰는 기능인가** → 주기 검증(로컬 캐시 ↔ 원격), 오류 시 전체 재동기화,
  쓰기 실패 재시도 큐를 설계에 넣었는가 (PRINCIPLE 3). 한 번의 동기화 실패도 기록 유실로
  이어지면 안 된다는 게 이 앱의 전제다.
- **업무 데이터를 로컬에 저장하려 하는가** → 안 된다. 로컬은 설정과 캐시만 (PRINCIPLE 4).
  Notion·Calendar 등 원본 서비스가 저장소다.
- **요약·판단·추출이 필요한가** → AI를 쓰지 않고 사용자 수동 조작 + 키워드 규칙으로 푼다
  (PRINCIPLE 1).
- **사용자를 브라우저로 보내는 흐름이 있는가** → OAuth 인증 동의처럼 불가피한 경우가 아니면
  실패로 간주한다 (PRINCIPLE 2).
- **알림을 추가하는가** → 기본은 pull이고 알림은 opt-in 설정으로 켜는 구조여야 한다 (PRD §5.7).
- **토큰·자격증명을 다루는가** → 보관 위치는 `CONVENTIONS.md`의 시크릿 규칙을 따르고, PRD Q2에서
  확정된 방식을 쓴다. 규칙 자체를 여기에 다시 적지 않는다 — 복제하면 갈라진다. 어느 쪽이든 값이
  코드·문서·커밋·로그·테스트 픽스처 어디에도 남지 않게 한다.
- **주기 폴링을 추가하는가** → 5개 서비스가 동시에 폴링하게 될 것을 전제로 주기를 정한다 (PRD R4).

## 3. 브랜치를 파고 유닛 단위로 구현한다

**엔진은 `ce-work`다 (필수).** 확정된 플랜 경로를 넘겨 구현을 돌린다. 단, `ce-work`는 자체적으로
커밋·푸시·PR까지 끌고 가려 하므로 **이 스킬의 4·5단계가 그 뒤를 대체한다** — merge 금지와
이중 테스트 게이트는 `ce-work`가 무엇을 하든 그대로 적용된다.

브랜치를 만든다 (`main`에서 시작, 이름은 `타입/기능-설명-번호`). 이후 커밋은 전부 이 브랜치에 한다.

플랜의 Implementation Unit 하나가 커밋 하나에 대응하는 게 기본이다. 유닛마다:

1. 핵심 로직이면 **실패하는 테스트부터** 쓴다 (Red → Green → Refactor). 테스트 이름은 한국어.
2. 구현한다.
3. 해당 러너를 돌려 통과를 확인한다.
4. 커밋한다 (한국어 Angular 컨벤션).

무엇을 테스트하고 무엇을 수동 확인으로 넘길지는 `references/verification.md`에 정리돼 있다.
요약하면 순수 로직과 API 응답 파싱은 반드시 테스트하고, 트레이·팝오버·알림 같은 OS 통합 표면은
단위 테스트로 잡히지 않으니 수동 체크리스트로 검증한다.

Rust에 새 파일을 만들 때는 `pomodoro.rs`처럼 **Tauri 타입에 의존하지 않는 순수 모듈**로 코어를
분리하고 Tauri 연결은 브릿지 모듈로 뺀다. 그래야 시간·네트워크를 주입해서 테스트할 수 있다.

## 4. 검증 게이트

PR을 열기 전에 전부 통과해야 한다.

| 게이트 | 명령 |
|---|---|
| Rust 단위 테스트 | `cd src-tauri && cargo test` |
| 프론트 단위 테스트 | `npm test` |
| 개발 스모크 | `npm run tauri dev` |
| 번들 검증 (알림 변경 시) | `npm run tauri build` 후 `.app` 실행 |

테스트 러너가 둘이라는 걸 잊기 쉽다. 한쪽만 돌리고 통과로 보고하지 않는다.

메뉴바 셸이나 창 표시/숨김을 건드렸다면 `references/verification.md`의 수동 체크리스트를 실제로
돌린다. 특히 **팝오버를 닫은 뒤 트레이 아이콘이 남아 있는지**는 과거에 실제로 깨졌던 항목이다.

그다음 자기 diff를 리뷰한다. 실험하다 버린 코드, 미사용 스캐폴딩, 디버그 출력, 시크릿이 남아
있는지 본다.

**그다음 `ce-code-review`를 돌린다 (필수).** 사용자가 요청할 때만 하는 게 아니다 — PR을 열기 전에
항상 거친다. 지적이 나오면 반영하고 **위 게이트를 처음부터 다시 돌린다.** 반영하지 않기로 한
지적이 있으면 PR "비고"에 이유와 함께 남긴다. 조용히 넘기지 않는다.

## 5. 문서를 맞추고 PR을 연다

같은 PR 안에서:

- `TODO.md` — 끝낸 체크박스를 체크한다.
- `PRD.md` / `SERVICES.md` — 기능이나 범위가 바뀌었으면 고친다. 오픈 퀘스천(§9)이 해소됐으면
  상태를 갱신한다.
- `PRINCIPLE.md` — 새로운 원칙이 생겼을 때만.

PR은 `.github/TEMPLATE/PR.md` 템플릿을 채워서 연다. UI가 바뀌었으면 스크린샷을 넣는다.
플랜에서 의도적으로 미룬 항목(Deferred)이 있으면 "비고"에 적고, 후속으로 남길 만하면
`TODO.md`에도 한 줄 추가한다 — 플랜 문서에만 적힌 후속 작업은 잊힌다.

**merge하지 않는다.** merge는 사용자가 직접 한다. PR 링크를 전달하고 멈춘다.

## 6. 배운 게 있으면 남긴다

디버깅에 한참 걸렸거나, 원인이 직관과 어긋났거나, 다시 밟을 것 같은 함정이었다면
`docs/solutions/`에 기록한다. **기록할 게 있다고 판단되면 엔진은 `ce-compound`다** — 남길지 말지의
판단은 여전히 재량이지만, 남기기로 했으면 손으로 쓰지 않는다.
기존 두 문서가 형식의 기준이다 — 증상, 안 통한 시도, 해결, 왜 통하는지, 예방책. "안 통한 시도"를 빼지 않는 게 중요하다. 다음에 같은 증상을 만났을 때
탐색 공간을 줄여주는 게 그 부분이다.

새로 알게 된 사실이 `CLAUDE.md`의 함정 목록에 들어갈 급이면 거기에도 한 줄 추가한다.

## 중간에 멈추고 보고해야 하는 상황

혼자 판단해서 밀고 나가면 손해가 큰 것들이다.

- 작업이 플랜 범위를 벗어나 다른 마일스톤 영역으로 번진다.
- PRD·PRINCIPLE과 어긋나야만 구현이 가능하다.
- 외부 서비스의 실제 응답이 플랜의 가정과 다르다 (스키마, 권한, rate limit).
- 사용자 계정에서만 할 수 있는 일이 필요하다 (Integration 생성, OAuth 동의, 스코프 승인,
  Notion DB 공유 설정).
- OS 통합이 리서치한 우회법으로도 동작하지 않는다.

## compound-engineering 엔진

각 단계의 엔진은 아래로 고정한다. **2~4단계는 필수다.** M1이 실제로 이렇게 만들어졌고
`docs/plans`·`docs/solutions`의 형식이 거기서 왔다 — 손으로 다시 쓰면 형식이 갈라진다.

| 단계 | 엔진 | 강제 |
|---|---|---|
| 2. 플랜 | `ce-plan` | 필수 |
| 3. 구현 | `ce-work` | 필수 |
| 4. 리뷰 | `ce-code-review` | 필수 |
| 6. 학습 기록 | `ce-compound` | 남기기로 했다면 필수 |

1·5단계는 이 스킬이 직접 처리한다 — 범위 게이트와 PR 작성은 프로젝트 규칙에 묶여 있어서
범용 엔진으로 대체되지 않는다.

**엔진이 프로젝트 규칙을 이기지 않는다.** CE 스킬들은 이 레포를 모른다. 범위 게이트(체크박스
하나), 원칙 체크리스트, 이중 테스트 게이트(`npm test` + `cargo test`), merge 금지는 엔진이 무엇을
하든 그대로 적용된다. 엔진 산출물이 이것들과 어긋나면 **엔진 쪽을 고친다.**

**건너뛰려면 먼저 보고한다.** 플러그인이 설치돼 있지 않거나, 작업이 너무 작아 엔진이 과하거나,
엔진이 실패했다면 — 조용히 손으로 처리하지 말고 이유를 사용자에게 말하고 동의를 받는다.
"안 쓰고 그냥 했다"가 사후에 드러나는 게 가장 나쁘다.
